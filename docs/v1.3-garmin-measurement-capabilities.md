It stores encrypted per-user keys and uses WordPress HTTP GET calls for activity data. The existing test_connection only verifies token acquisition. It does not prove every measurement resource is authorized or contains data. Current activity methods and scheduled sync do not retrieve health measurements. Do not attach health sync automatically to existing activity sync without category-specific opt-in.

## Weight and composition contract

DateWeightDTO documents:

| Field | Type/meaning | Unit certainty |
| --- | --- | --- |
| weight | Number; weight measurement | Explicitly kilograms for DateWeightDTO |
| bmi | Number; body mass index | BMI measurement, not weight |
| bodyFat, bodyWater | Numbers | Entry descriptions omit units; WeightAverageDTO explicitly calls the corresponding averages percentages. Confirm actual entry semantics before normalizing/displaying |
| boneMass, muscleMass | int32 | Units unspecified; do not assume kg or grams |
| physiqueRating, visceralFat | int32 | Ratings/measurement descriptions; do not label as percentages or mass |
| metabolicAge | Number | Preserve source meaning; not an independently calculated result |
| date | date-time string | User-local date/time |
| calendarDate | String | User-local YYYY-MM-DD |
| timestampGMT | date-time string | GMT measurement timestamp, documented format includes offset |
| weightDelta | Number | Previous-reading difference; unit not explicitly stated |

No stable measurement ID, source-device identifier, modification timestamp or explicit timezone identifier is declared in DateWeightDTO. User profile/account IDs must not be treated as measurement IDs. Optional/missing properties must remain absent; do not interpret missing or undocumented sentinel values as real zero measurements.

WeightRangeDTO contains dailyWeightSummaries, totalAverage, previousDateWeight and nextDateWeight. Adjacent entries are graph context outside the requested range, not additional in-range readings. DailyWeightSummary contains summaryDate, numOfWeightEntries, minWeight, maxWeight, latestWeight and allWeightMetrics. latestWeight can duplicate a member of allWeightMetrics. totalAverage is a range aggregate, not an individual measurement or a daily average.

Prefer the all-entries path for initial per-reading import, subject to payload confirmation; if using range, explicitly request includeAll=true and import its allWeightMetrics once rather than combining latestWeight and contextual/aggregate fields.

## SpO2 contract and implications for step 03

The response explicitly supports BOTH summaries and samples:

- averageSpO2: Garmin average percentage during the reporting window.
- lowestSpO2: lowest percentage during that window.
- latestSpO2 and latestSpO2TimestampGMT/Local: most recent percentage and time.
- lastSevenDaysAvgSpO2: trailing seven-day baseline, not today's average.
- avgSleepSpO2 and avgTomorrowSleepSpO2: distinct sleep summary fields; exact sleep attribution/availability needs payload verification.
- spO2SingleValues: individual reading rows, whose columns are described by spO2SingleValuesDescriptorList.
- spO2HourlyAverages: hourly averaged rows with their own descriptor list; not individual samples.
- Separate monitoring-environment values/descriptors are also present.

Decode columns from descriptor keys/indexes rather than fixed positions. The individual descriptor schema declares index/key fields but does not enumerate permitted keys or specify timestamp encoding. Hourly descriptors describe timestamp, spo2Level and monitoringEnvironmentLevel; the actual timestamp unit still needs confirmation.

Preserve calendarDate and reporting/sleep window boundaries. GMT/local boundary strings are explicitly documented WITHOUT an offset or Z; interpret GMT fields as UTC by their contract, never by the server default timezone. Do not infer a single permanent offset from a day spanning a DST transition. A Garmin reporting window may differ from site-local midnight boundaries.

Use the Garmin average as a separately identified provider summary where present. Do not average daily summaries together with raw readings or hourly averages. An optional calculated mean requires verified raw sample semantics, valid unique samples, stated coverage and method; it cannot be claimed equivalent to Garmin's average. No average calculation or calendar attribution is implemented in this phase.

## Identity and duplicate implications

The documented responses do not provide a stable per-reading ID for weight or SpO2 samples. Later persistence must support owner/provider/type/time plus a normalized value fingerprint and distinguish summary rows from samples. A summary can be keyed by category, provider calendar date and reporting-window identity and refreshed on reimport.

An identical timestamp/value/source can be skipped safely under the defined fallback policy, but changed values at the same timestamp cannot automatically prove a correction without reliable identity. Retain or flag ambiguity rather than silently overwriting a distinct reading. Exact duplicate samples returned in overlapping windows should display once. Do not deduplicate solely by equal numeric values or calendar date.

## Limits and unresolved payload checks

- Weight endpoints specify inclusive date ranges and local calendar semantics. Neither declares pagination, a maximum range, rate limits or retention/backfill guarantees. Absence of pagination documentation is not proof of unlimited results.
- SpO2 takes one calendar date and declares 400/401/403/500 failures. No retention or request quota is given.
- Do not borrow the one-year limit documented for daily summaries/Body Battery and apply it to these measurements as an API guarantee.
- Later requests should use bounded windows, response-size limits, appropriate error handling and retries/backoff. Empty, missing, unauthorized and transport-failed responses must remain distinct; none should delete existing data.
- Authorized account checks still need to establish field presence/null/sentinel handling, composition units, sample timestamp units/descriptors, multiple readings per day, available history, and response behavior. Record only redacted structural evidence; never commit personal payloads, keys or tokens.
- Live record retrieval requires the user's installed site's stored key or another explicitly configured secure execution environment. Connected GitHub tools do not execute WordPress or expose those keys. Do not ask the user to paste a key into chat.
- No production health data was read, stored or imported; no schema, runtime services, versions, release workflow, ZIP, main, tags or SVN changed.
