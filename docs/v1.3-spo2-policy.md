# v1.3 step 03 — SpO2 interpretation and display policy

Decision date: 2026-10-29. This is the implementation contract for later storage, import and calendar phases, not a claim that those features already exist. It builds on [the verified Personal API contract](v1.3-garmin-measurement-capabilities.md). No live personal response has been inspected.

## Primary daily value

Use valid Garmin averageSpO2 as the primary provider-reported summary. Label it **Garmin average SpO2**, with the provider calendar date and reporting window available in day details. Do not call it a full 24-hour average unless the returned window actually establishes that coverage. Never replace it with an arithmetic mean merely because individual readings are also present.

Provider summaries, individual samples, hourly averages, latest-reading references, sleep summaries and seven-day baselines are different record roles. They must not share a sample count or be combined into one average.

| Available data | Primary display | Additional detail |
| --- | --- | --- |
| Valid Garmin average, with or without samples | Garmin average SpO2 | Reporting window; available unique imported sample count clearly separate from Garmin's averaging denominator |
| No valid Garmin average; verified, conflict-free raw samples with at least two distinct instants | Calculated mean of imported readings | Method, unique usable count, first/last sample time, partial coverage notice |
| No valid Garmin average; one verified sample | SpO2 reading | Sample time; do not label as a daily average |
| Only valid latestSpO2 plus verified timestamp | Latest SpO2 reading | Treat as a provider latest-reading reference, not an extra sample |
| Only hourly or sleep summaries | Available SpO2 summaries | Show their exact roles; no invented daily average |
| No valid numeric data | No numeric SpO2 indicator | Show import/validation status separately; missing is not zero |

A valid but inconsistent provider summary may still be shown as Garmin-reported, with a data-consistency notice. It must not be silently repaired using samples. A Garmin average is not evidence that all individual readings were returned.

## Validity and field interpretation

- Accept finite numeric percentages strictly greater than 0 and at most 100; retain decimal precision for computation. Zero, null, nonnumeric, nonfinite and out-of-range values do not become measurements. This is structural validity, not a clinical interpretation or a guarantee of measurement accuracy.
- Do not round before duplicate comparison or averaging. Display percentages to at most one decimal place with source labeling; retain original normalized precision in storage.
- Decode individual rows using spO2SingleValuesDescriptorList keys/indexes. Reject missing/duplicate/out-of-range column mappings or malformed rows from calculation. Do not use guessed positions.
- A sample timestamp encoding must be confirmed by authoritative documentation or authorized payload verification before that sample format is enabled. Do not guess seconds versus milliseconds from magnitude alone.
- Unknown monitor/environment codes remain unknown. Do not infer awake/sleep categories from them.
- A malformed sample section must not prevent independently valid provider summary fields from being imported. Report the skipped sample rows and reason without logging private payloads.
- latestSpO2 can point to an existing sample: do not append it as another sample. It can be displayed as a latest-reading reference when its own timestamp/value is valid.
- lowestSpO2 is Garmin's reporting-window minimum, not necessarily the minimum of imported samples. Any sample-derived minimum must have a different label.

## Fallback calculated mean

Enable this fallback only after the raw sample contract has been verified, and only when averageSpO2 is absent/invalid.

1. Select individual samples belonging to the provider report day, within the verified reporting window when present.
2. Resolve descriptor mapping, timestamp units and percentage validity.
3. Deduplicate repeated copies using owner/provider/role/timestamp/value identity and retain provenance separately.
4. Do not count a latest-reading reference, hourly average, sleep average, seven-day baseline or Garmin daily average.
5. If two different percentages remain at the same instant without a reliable source identity or correction ordering, preserve the ambiguity but exclude that instant from calculation. Do not choose a value based on arrival order.
6. If any sample parsing errors, unresolved conflicts or known truncation affect the candidate report, withhold fallback averaging and show valid readings plus a clear incomplete-data status. Ordinary gaps in an otherwise successfully decoded returned sample set do not imply continuous coverage.
7. With at least two unique usable instants, compute the unweighted arithmetic mean of those percentages. Label **Calculated mean of imported readings**, never a continuous/time-weighted daily average. With one sample, display the reading only.
8. Store calculation method/version, usable unique count, first/last instant, provider date/window and source provenance. Keep any derived result separate from provider-reported summaries.
9. Recompute from the unique eligible samples when new usable samples are imported. A later valid Garmin average takes display priority without deleting source samples or changing the historical calculation's provenance.

Irregular sampling is why this fallback explicitly describes the imported readings rather than claiming to reproduce Garmin's algorithm. Do not interpolate missing readings or average hourly summaries to fabricate a daily value.

## Calendar day and sleep attribution

- The Garmin SpO2 calendarDate is authoritative for placement of that provider report and its indicator. Preserve it independently of UTC timestamps and the WordPress site's timezone.
- Show the report once on that provider calendar day. In details identify it as Garmin's calendar date and expose source times/reporting window so travel or site-timezone differences are understandable.
- For samples, retain their canonical UTC instants plus supplied local values, provider report membership and any verified per-reading offset. A sample appearing in adjacent overlapping reports is stored once; report membership must not multiply its global sample count.
- For fallback day averaging, use one owning day per sample: verified sample-local calendar date when supplied, otherwise an unambiguous provider reporting-window assignment. If overlapping reports imply conflicting ownership and no verified local date resolves it, exclude the ambiguous sample from day calculations and flag it.
- Do not use the PHP/server timezone to parse Garmin fields. GMT fields documented without Z are UTC by contract. Local strings without an offset cannot by themselves establish a UTC instant.
- Retain start/end window pairs and exact precision. Do not assign one inferred offset to an entire DST-changing day.
- Keep avgSleepSpO2 and avgTomorrowSleepSpO2 separate from averageSpO2. Never add them as readings or calculate a mean of these averages.
- Preserve sleep start/end GMT/local boundaries and the containing provider calendarDate. Until the sleep attribution contract is verified, display these only in that report's details with explicit sleep-window labels; do not create a second calendar indicator on a guessed sleep date.

This Garmin-specific date rule does not silently change existing workout calendar placement. Step 04 must represent provider date and UTC measurement time independently.

## Reimports, corrections and freshness

- One current provider report per owner/provider/report role/calendarDate. Reimport replaces its summary snapshot atomically when a later successful serialized fetch changes it, retaining audit metadata. Changed window boundaries refresh the same current report rather than creating a second current day summary.
- Serialize overlapping fetch/write operations for the same provider report day so older concurrent responses cannot win by finishing last. Store fetch time and payload fingerprint; the schema exposes no provider revision timestamp, so do not claim freshness stronger than the latest successful observation.
- Skip unchanged report snapshots. Do not create duplicate indicator rows from repeated summary imports.
- Sample fallback identities do not include the containing response date, so adjacent report overlap does not duplicate samples. Preserve report associations separately.
- Equal values at distinct times remain distinct readings. Different values at the same instant remain an unresolved correction/conflict unless reliable identity or source revision proves replacement.
- Reimport failures, missing records and partial/empty responses do not erase existing readings or summaries. Absence of a previously seen sample is not proof of deletion. Track completeness and last successful sync separately.
- An import summary counts newly inserted/updated/skipped records, not new provider measurements inferred from aggregate fields.

## Calendar accessibility and privacy

One accessible SpO2 indicator per calendar day, in both grid and mobile agenda, irrespective of number of samples or summary roles. Its text identifies the primary value and provenance; color alone never conveys meaning. Day details can list the provider average, available unique sample count, imported readings, sleep/hourly summaries and reporting window without conflating them.

Missing/invalid data never displays as 0%. A seven-day baseline must not appear as today's average. No clinical thresholds, diagnostic colors, alarms or training-clearance conclusions are introduced. Existing public results, sharing and external REST access do not authorize these records.

## Implementation acceptance cases

These are required later behavior tests, not tests already executed by this documentation phase.

| Synthetic scenario | Required result |
| --- | --- |
| Garmin average 96.4 with raw samples 94 and 98 | Primary 96.4% Garmin average; sample count 2; no replacement with 96 |
| No provider average; verified samples 94 and 98 at distinct times | Calculated mean 96%; count 2, partial coverage/method labeled |
| Above stream repeated in overlapping imports | Same two samples and same mean; one day indicator |
| Equal 97 readings at two different times | Both retained; count 2 |
| Same timestamp with 94 and 98; no correction identity | Retain conflict; withhold fallback mean |
| One valid sample and several null/zero/invalid rows | Display valid reading, not a fabricated daily average; report invalid rows |
| Provider average plus malformed sample descriptors | Preserve/display valid provider average; flag skipped samples |
| Daily average absent, only hourly/sleep/seven-day averages | Show exact available summaries; no derived daily average |
| Latest reading duplicates a raw sample | No extra sample |
| Same report date reimported with changed average/window | Refresh one current report; one indicator, no duplicate summary |
| UTC date differs from provider calendarDate | Indicator stays on provider report day; times retain provenance |
| Adjacent reports contain the same sample | One stored sample; associations do not double-count |
| Failed/empty/partial refresh | Existing data preserved; sync status conveys failure/incompleteness |
| DST transition/travel and missing local offset | Preserve source fields; do not invent timestamp/day ownership |
| Unauthorized calendar/public results request | No measurement disclosure |

## Remaining verification gates

Actual descriptors and sample timestamp encoding, null/sentinel behavior, reporting coverage and sleep attribution require authorized account evidence before affected parsing paths are enabled. Supported documented Garmin summaries can be implemented independently of unresolved raw-sample formats.

No measurements were fetched, no runtime code/storage/schema changed, and no release/package/SVN actions were performed in step 03.
