# v1.3 step 05 — private duplicate-safe persistence

Health_Measurement_Store saves a bounded normalized report bundle, not an arbitrary Garmin payload. No transport, import UI, calendar retrieval/display or scheduled health sync is enabled here. Database schema remains 1.3 and plugin version remains 1.3-dev.

## Access and transaction boundary

save_report(owner, report, observations) and get_for_user(id, owner) require the authenticated current owner with swimlog_manage_own_workouts. Anonymous, other-owner and missing-capability calls are denied. No administrator cross-owner exception is granted by this service. The only accepted provider in this phase is garmin. BP record validation does not authorize a BP endpoint.

Before writes, validate categories/roles, exact dates, explicit UTC/local timestamps up to microseconds, verified offsets, normalized values/units, grouped BP pairs, allowlisted bounded provenance and snapshot fields. Unknown fields (including arbitrary payload/key containers) are rejected. No time is inferred from a local string. Missing UTC requires a stable source ID; unresolved dates stay null. Values use canonical decimal strings (up to nine fractional digits, no truncation); unsupported numeric encodings fail rather than guess units/precision.

The service refuses non-InnoDB tables and existing caller transactions. It acquires a zero-wait MySQL/MariaDB connection advisory lock scoped to site prefix/owner/provider/category before beginning a transaction. This serializes overlapping report-day writes, not just identical days. Busy returns a retriable WP_Error. Locks are released in finally and all report/observation/member writes roll back on failure. HTTP fetch scheduling is still step 06/09; report fetched_at_utc must be the actual fetch observation time, not a fabricated provider revision.

Database read caching now excludes advisory lock/release calls and transaction-state reads. Caching those calls could falsely report a lock as acquired or a transaction as absent. Existing query preparation and owner-scoped caching remain intact.

## Identity and counts

| Input case | Handling |
| --- | --- |
| Same stable source ID, provider/category/role, same content | Skip |
| Same stable ID, changed content | Require confirmed_correction=true and expected_content_hash matching current row; otherwise fail bundle without overwrite |
| No stable ID | SHA-256 of provider/category/role/canonical UTC timestamp/canonical grouped values |
| Repeated copies or adjacent report overlap | Reuse one observation and one membership per report; containing report date is not part of observation identity |
| Equal values at different instants | Retain separate observations |
| Differing observations at the same instant | Retain; conflict counts and owner lookup expose ambiguity; never arrival-order winner |
| Same identity under another owner | Separate private row |
| Old provider report snapshot | Reject older fetch times; reject changed summary content at equal fetch time |
| Changed provider summary/window at a later fetch | Update one current owner/provider/category/day report |
| Failed/empty refresh | Failure rolls back; absence never deletes previous observations or memberships |

Report summary status (added/updated/skipped) is separate from observation counts (added/updated/skipped/conflicts/failed). Counts describe the successfully committed incoming stream; repeated copies count as skips, not new measurements. Failed bundles return WP_Error with no successful import counts; the future import orchestrator counts failed bundles. No duplicate-history rows are appended; created/updated/fetched audit fields and memberships are retained.

Context/provenance and observation placement do not create a second identity. A conflicting date/time/content update to a fallback-identified observation fails conservatively rather than silently reassigning it. Exact stable-ID correction uses compare-and-swap to protect against a stale writer. Different source IDs at the same instant are conservatively ambiguous, even if numeric values match.

get_for_user derives same-instant ambiguity dynamically for both original and new observations. It does not persist a stale one-sided conflict flag. Later SpO2 averaging must use this ambiguity policy and exclude unresolved conflicts. No SpO2 mean is calculated in this phase.

## Payload shape for later adapters

Report: provider, category, calendar_date, fetched_at_utc (whole-second ISO UTC), summary (named value/unit entries), context (allowlisted strings). Observations: role, optional verified external_id, optional confirmed_correction/expected_content_hash, observed_at_utc, source_local_time, source_offset_seconds, calendar_date, date_basis, values and provenance.

Categories: weight, body_composition, blood_pressure, spo2. Observation roles: sample; SpO2 additionally hourly_average, sleep_average, calculated_mean. SpO2 provider summary keys: average, lowest, latest, sleep_average, next_sleep_average, seven_day_average. Summaries never become sample rows. Composition kg/% mappings describe normalized input only; adapters cannot claim Garmin's undocumented mass units are already verified.

JSON envelopes carry version 1. Values and provenance remain structured, not raw personal response archives. Report contexts support normalization_version, device, source_format, window_start/end_utc/local, method, coverage and source_revision; unsupported content fails validation.

## Regression evidence

HealthMeasurementStoreTest runs on every supported PHP and covers equivalent numeric/timestamp encodings, microseconds, repeated DST local hours, invalid dates/offsets, unknown time identities, BP pairs, units/value validation, payload bounds and correction preconditions.

health-measurement-integration.php exercises real staged WordPress/MariaDB: duplicate streams, report overlap, distinct same-day readings, two-sided conflicts, stable-ID compare-and-swap, stale report rejection, owner isolation/capability checks, a competing DB connection lock plus successful retry, caller transaction preservation, and injected membership failure rolling back the complete bundle. It removes all synthetic user rows afterward. Existing schema and browser suites continue to run.

No personal health data or credentials are included in tests. No schema increment, distribution ZIP, main/tag/release or SVN changes.
