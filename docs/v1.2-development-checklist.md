## Database boundary exceptions

Core has no CRUD API for the normalized custom tables. `Database::read()` and `Database::write()` contain the only new centralized direct-query exceptions, on individual calls rather than across a file. Domain services bind identifiers with WordPress 6.2 `%i` and values with typed placeholders. The read boundary receives caller-prepared SQL; the write boundary preserves wpdb CRUD escaping and fixed/prepared transaction/query commands.

| Call | Technical justification |
| --- | --- |
| `get_results` | Custom-table collections; request-only cache, at most 128 entries of at most 1,000 rows, invalidated on every observed mutation. |
| `get_row` | Owner-scoped custom-table row reads; same cache policy, returning cloned objects to prevent callers changing cached rows. |
| `get_col` | Custom-table IDs and aggregates; same cache policy, arguments/output mode included in the key. |
| `get_var` | Custom-table scalar reads and schema SHOW checks; SELECTs use the cache, SHOW bypasses it. |
| `insert` | Core wpdb field escaping; mutation invalidates before execution and preserves insert IDs/return values. |
| `update` | Core wpdb field/where escaping; mutation invalidates before execution, including failed attempts. |
| `delete` | Core wpdb where escaping; mutation invalidates before execution. |
| `replace` | Core wpdb field escaping; mutation invalidates before execution. |
| `query` | Fixed transaction commands or domain-prepared custom-table statements; no write-result caching. |

Transactions bypass reads from cache. The WordPress query filter observes writes outside these services, including core post/meta changes. No cache survives the HTTP request, so no private rows cross requests or require cross-worker invalidation. Non-deterministic/locking reads and oversized result sets bypass storage. Failed reads are not stored. Cache keys also identify the wpdb object and prefix.

## Six retained metadata performance exceptions

These are narrow source-line annotations, not workflow ignore codes. They retain core WordPress APIs and existing metadata associations without a schema migration. The generic warnings describe possible performance costs; they do not establish an unsafe or incorrect query. These queries can still merit profiling if an installation accumulates unusually large private post histories.

| Location and rule | Technical justification |
| --- | --- |
| `Planned_Structure_Link::for_plan`, `slow_db_query_meta_key` | Existing plan-link metadata on private structures, restricted by owner; retrieves at most two IDs to detect corrupt duplicates. |
| Same lookup, `slow_db_query_meta_value` | Exact validated plan ID is the existing relationship key. Removing its comparison would link unrelated prescriptions. |
| `Training_Plan_Collection::attach`, `slow_db_query_meta_query` | Existing plan-plus-sequence uniqueness check, restricted by owner/private type. Retrieves two IDs and excludes the current structure in PHP, replacing `post__not_in`. |
| `Training_Plan_Collection::workouts`, `slow_db_query_meta_key` | Numeric sequence ordering is stored in existing metadata. Core ordering preserves legacy plan order and the supported 500-workout maximum. |
| Same method, `slow_db_query_meta_query` | Exact plan membership is stored in existing metadata; owner/type/status restrictions and core cache behavior remain intact. |
| `Training_Plan_Bulk_Import::run`, `slow_db_query_meta_query` | Exact validated SHA-256 duplicate-import lookup across one owner's private plans, returns one ID. Core manages metadata caches/invalidation. |
