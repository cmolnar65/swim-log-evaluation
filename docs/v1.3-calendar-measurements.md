# v1.3 step 07 — owner-only calendar measurement retrieval

Calendar_Measurements::for_user provides a private projection of stored health reports and observation groups. The separate GET /swimlog/v1/calendar/measurements route supplies it to an authenticated owner browser. Visible icons, indicators, day dialogs and browser requests for this new route are step 08, not implemented here.

## Authorization

The service requires current-owner identity and both swimlog_view_own_results and swimlog_manage_own_workouts. The REST route additionally requires a validated WordPress logged-in cookie for that same owner and X-WP-Nonce verified for wp_rest. No anonymous, cross-user, manage-all-users, Public Results, Public Open-Water Routes or external API opt-in bypass exists. Application Password authentication alone cannot read this route.

Existing /calendar, portability endpoints and public shortcodes are unchanged. WordPress administrator access to another swimmer's ordinary calendar does not include that swimmer's health records. Responses are private, no-store. Direct trusted server-side service calls remain current-owner/capability scoped.

## Date and grouping contract

Queries are owner-indexed, half-open provider_date/calendar_date ranges. The range is strictly validated and capped at 62 inclusive days for normal six-week calendar grids. Reports use their source provider day; observations use their stored attributed day, independent of UTC midnight and later site timezone changes. Null/unresolved dates are excluded, never guessed.

Response days contain:
- reports: provider-reported summary values and whitelisted valid GMT/local reporting/sleep window fields.
- readings: individual grouped samples; BP pairs and body composition values stay together.
- aggregates: hourly, sleep or recognized precomputed observations; never counted as individual readings.

Provider SpO2 average, latest/minimum, sleep and seven-day baseline stay distinct named summary fields. Retrieval does not compute or replace averages. Same-instant conflicts are derived with an indexed owner/source/category/role/time lookup, including peers outside the displayed date range; both ambiguous observations are flagged. Report membership is not joined into readings, so overlapping reports do not duplicate observations.

Empty import bookkeeping reports do not create numeric reports/indicators. Unsupported providers/categories/roles, malformed JSON envelopes/units or invalid source times are withheld with invalid_records. Source values are validated through the same pure canonical value rules as persistence.

## Data minimization and bounds

Only projected numeric values, explicit units/roles/source label, authorized internal observation ID, date basis, source times/offset and conflict state are returned. No external IDs, owner/account IDs, identity/content hashes, raw JSON payloads, arbitrary provenance, private notes or device details are exposed.

Fetch at most 501 reports and 2,001 observations to detect overflow; limits are 500 and 2,000. Dense ranges fail with HTTP 413 rather than silently truncating data or implying full sample coverage. Read errors fail rather than manufacture an empty successful calendar. No schema change.

## Regression scope

CalendarMeasurementsTest covers current-owner/capability rules and strict calendar-grid ranges. Real WordPress/MariaDB integration covers stored provider dates differing from UTC, timezone/DST invariance, same-day distinct samples, grouped BP, provider/sample/aggregate separation, overlap and two-sided conflict flags, unresolved dates, private safe projections, real cookie/nonce permissions, missing/invalid nonce and noncookie denial, cross-owner administrator denial, unchanged existing calendar/portability responses, malformed storage and dense-range failure.

Synthetic fixtures only; no live personal records, production cookies or credentials are used. The existing PHP matrix, strict staging Plugin Check and integrations/browser checks remain enabled.
