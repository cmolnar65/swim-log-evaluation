# iHealth app setup and OAuth verification

## Scope

The WordPress administrator screen **SwimLog → iHealth App Setup** stores the iHealth developer application's Client ID, Client Secret and selected API categories, then lets a signed-in administrator authorize an iHealth account to verify the app credentials and requested categories.

This step does **not** import, display, synchronize or otherwise process iHealth measurements or activity records. It creates no database tables and does not change the private measurement model, Garmin behavior, REST API, public workout output or standalone application. Category selection identifies the iHealth APIs to request during consent; it is not evidence that an importer exists or that a category's live account data has been tested.

## iHealth developer portal values

Register the callback URL shown on the WordPress setup screen. For `https://cmolnar.com`, the expected callback is:

```text
https://cmolnar.com/wp-admin/admin-post.php?action=swimlog_ihealth_oauth_callback
```

Set **Redirect Domain** to the HTTPS origin of the WordPress site's `home_url()`. For the site above, that is `https://cmolnar.com`. iHealth must allow the callback URI supplied during authorization, including its `action` query parameter. SwimLog adds a unique short-lived `state` query parameter for each attempt; do not register a state value.

The **Authorization Removal Callback URL** is a separate portal setting. The OAuth callback above does not handle authorization removal. Do not change or repurpose that portal setting as part of this setup.

## Setup and consent flow

1. In WordPress administration, open **SwimLog → iHealth App Setup**.
2. Enter the Client ID and Client Secret from the iHealth developer portal and select only the data categories the integration may request. A saved secret is not displayed again; leave its field blank to keep the existing value.
3. Save the app settings, then select **Authorize with iHealth and verify**.
4. Sign in to the intended iHealth account and approve the requested categories at iHealth.
5. Return to the same signed-in WordPress administrator session. The screen reports the categories iHealth confirmed and the access token expiry time.

The app secret is encrypted in a non-autoloaded WordPress option. OAuth state is generated randomly, expires after ten minutes, and is stored only as a hash bound to the initiating administrator. The callback accepts only that administrator, consumes the state once, and does not echo provider errors, codes, or response payloads. A callback received after signing out or changing WordPress administrator accounts must be restarted from the setup screen.

Access token, refresh token and iHealth account identifier are encrypted in the authorizing administrator's private user metadata. The setup page only receives a limited status projection: connected state, approved categories and expiry. Tokens and account identifiers are not displayed or returned through a REST/public endpoint. The current screen does not refresh tokens automatically; reauthorize if the grant expires.

The encryption key is derived from the WordPress authentication salt. If that salt changes, previously stored iHealth credentials and tokens can no longer be decrypted; enter the app credentials again and authorize the account again. Saving different app credentials or category selections invalidates the visible grant because its stored app revision no longer matches. Old encrypted per-user grant data is not automatically removed for other administrators when global settings change.

## Privacy and validation

OAuth is a user-consent step, not a health-data transfer. Do not place real Client IDs, Client Secrets, authorization codes, state values, access/refresh tokens, account identifiers, or provider payloads in Git, test fixtures, Actions inputs/logs, screenshots, support reports or packages. Regression tests must use synthetic values and mock the provider response.

Validation for this step covers encrypted credential storage, secret omission from the admin projection, authorization state and administrator binding, one-use callbacks, encrypted private per-administrator token storage, and rejection of incomplete scope grants without replacing an existing grant. It does not establish physical-device behavior, live account category coverage, data importer correctness, or the user's real-life acceptance of v1.3.

## Current development limits

- iHealth weight, blood-pressure, glucose, SpO2, activity, sleep, sport, temperature and heart-rate categories can be selected for authorization when offered by the developer application.
- No iHealth measurement or activity importer is included by the setup/verification feature.
- No blood-pressure import support is claimed until a supported Personal API endpoint and response contract are confirmed and a private importer is implemented and tested.
- No database schema change is required. v1.3 remains on release hold; automated tests and staging checks do not imply user acceptance.
