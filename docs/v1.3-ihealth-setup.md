# iHealth app setup and OAuth verification

## Scope

The WordPress administrator screen **SwimLog → iHealth App Setup** stores the iHealth developer application's Client ID, Client Secret and selected API categories, then lets a signed-in administrator authorize an iHealth account to verify the app credentials and requested categories.

The plugin includes a private, server-side transport and manual, administrator-only importers for one bounded page from the iHealth Personal API weight and blood-pressure endpoints. They require the currently signed-in grant-owning WordPress administrator, check both the saved application category and account-granted category, use the encrypted grant and matching app signing codes internally, and refuse requests when the access token is expired or within 60 seconds of expiry. Provider redirects are disabled, responses are size-limited, and provider errors or payloads are not logged or echoed in error messages. Pagination links are not followed; an administrator explicitly requests each numbered page.

Each importer accepts a date range of at most 90 days ending no later than today and pages 1–20. The weight importer reads `WeightDataList`, `DataID`, `MDate`, `WeightValue`, and `WeightUnit`. Only weight units explicitly recognized from `WeightUnit` are converted to canonical kilograms. The original numeric composition fields `BMI`, `BoneValue`, `DCI`, `FatValue`, `MuscaleValue`, `VFR`, and `WaterValue` are retained in owner-scoped private provenance under their original API names and with units marked `unknown`; they are not displayed, converted, aggregated, compared, interpreted or used in calculations. `Note` and source/device identifiers other than the private record identity are not retained in these raw fields.

The blood-pressure importer uses the account-verified `bp.json` route and reads `BPDataList`; the current public Personal API documentation does not provide a complete schema for this response. In the confirmed account response, top-level `BPUnit` was `mmHg`, and records included integer `HP`, `LP`, and `HR` fields. The importer maps those observed field names to systolic pressure, diastolic pressure, and pulse respectively. This mapping is limited to the response evidence and field names; it does not classify, diagnose, interpret, or derive health conclusions. Unsupported or missing units and incomplete pressure pairs are rejected without storing the record. The observed `DataID` is used only as private idempotency identity, and `MDate` supplies the timestamp using the seconds convention already used by the iHealth weight importer. `BPL`, `IsArr`, `Lat`, `Lon`, `Note`, `LastChangeTime`, `DataSource`, `TimeZone`, `time_zone`, and `measurement_time` are not stored or exposed.

Private measurement rows remain owner-scoped and are available only to the owning signed-in administrator through the existing private calendar projection. No health values or raw provenance are added to public workout output or new REST routes. No database tables or schema version changes are introduced, and Garmin behavior remains unchanged.

## Cross-provider duplicate handling

Weight duplicate checks compare only records belonging to the same WordPress owner and different providers. A same-instant reading whose normalized kilograms round to the same gram is counted as an exact cross-provider duplicate and omitted from calendar readings. Both provider source records and their private identities remain stored, so a repeated import cannot erase source provenance. A same-day equal-weight record at a different time is retained and counted as a possible duplicate. Different weights at the same instant are retained and counted as a conflict. The import notice reports counts only; it does not show measurement values or provider payloads.

## iHealth developer portal values

Register the callback URL shown on the WordPress setup screen. For `https://cmolnar.com`, the expected callback is:

```text
https://cmolnar.com/wp-admin/admin-post.php?action=swimlog_ihealth_oauth_callback
```

Set **Redirect Domain** to the HTTPS origin of the WordPress site's `home_url()`. For the site above, that is `https://cmolnar.com`. iHealth must allow the callback URI supplied during authorization, including its `action` query parameter. SwimLog adds a unique short-lived `state` query parameter for each attempt; do not register a state value.

The **Authorization Removal Callback URL** is a separate portal setting. The OAuth callback above does not handle authorization removal. Do not change or repurpose that portal setting as part of this setup.

## Setup and consent flow

1. In WordPress administration, open **SwimLog → iHealth App Setup**.
2. Enter the Client ID and Client Secret from the iHealth developer portal and select only the data categories the integration may request. A saved secret is not displayed again; leave its field blank to keep the existing value.
3. For manual weight import, enter the SC and Weight API SV. For manual blood-pressure import, enter the SC and Blood Pressure API SV. The API-specific SV values are separate. They are encrypted and never redisplayed; leave a saved field blank to retain its value.
4. Save the app settings, then select **Authorize with iHealth and verify**.
5. Sign in to the intended iHealth account and approve the requested categories at iHealth.
6. Return to the same signed-in WordPress administrator session. The screen reports the categories iHealth confirmed and the access token expiry time.
7. Use the separate manual weight or blood-pressure import form to choose an inclusive date range and one page number. Review the count-only result; enter the next page manually when the screen reports that more data may be available.

The app secret, SC, Weight API SV, and Blood Pressure API SV are encrypted in a non-autoloaded WordPress option. OAuth state is generated randomly, expires after ten minutes, and is stored only as a hash bound to the initiating administrator. The callback accepts only that administrator, consumes the state once, and does not echo provider errors, codes, or response payloads. A callback received after signing out or changing WordPress administrator accounts must be restarted from the setup screen.

Access token, refresh token and iHealth account identifier are encrypted in the authorizing administrator's private user metadata. The setup page only receives a limited status projection: connected state, approved categories and expiry. Tokens and account identifiers are not displayed or returned through a REST/public endpoint. The private API transport does not refresh tokens; it refuses calls near expiry and asks the administrator to reauthorize. Automatic refresh remains disabled until the official Personal API refresh-token contract, including rotation and expiry behavior, is verified.

The encryption key is derived from the WordPress authentication salt. If that salt changes, previously stored iHealth credentials and tokens can no longer be decrypted; enter the app credentials again and authorize the account again. Saving different app credentials or category selections invalidates the visible grant because its stored app revision no longer matches. Old encrypted per-user grant data is not automatically removed for other administrators when global settings change.

## Privacy and validation

Do not place real Client IDs, Client Secrets, SC/SV codes, authorization codes, state values, access/refresh tokens, account identifiers, measurement values, or provider payloads in Git, test fixtures, Actions inputs/logs, screenshots, support reports or packages. The plugin does not log OAuth URLs, callback parameters, credentials, tokens or provider responses. Hosting-level HTTP access logs may include callback query strings; configure server logging to restrict or redact those URLs. Regression tests must use synthetic values and mock the provider response.

Validation covers encrypted credential storage, secret omission from the admin projection, authorization state and administrator binding, one-use callbacks, encrypted private per-administrator token storage, rejection of incomplete scope grants without replacing an existing grant, and synthetic tests for owner/scope checks, fixed HTTPS requests, safe transport options, malformed inputs and generic provider failures. A sanitized authorized account probe confirmed the `bp.json` response keys (`BPDataList`, `BPUnit`, pagination fields), record field names/types, and `BPUnit=mmHg`; measurement values, IDs, dates, and raw payload were not shared or added to the repository. Automated tests do not establish full account history coverage, other account/device response variants, physical-device behavior, or the user's real-life acceptance of v1.3.

## Current development limits

- iHealth weight, blood-pressure, glucose, SpO2, activity, sleep, sport, temperature and heart-rate categories can be selected for authorization when offered by the developer application.
- Manual weight/body-composition and blood-pressure/pulse page importers are included. No other iHealth measurement or activity importer, background synchronization or automatic token refresh is enabled.
- Synthetic fixtures cover BP mapping, privacy filtering, unit rejection, idempotent retries, owner/scope checks and private calendar output. The sanitized account probe confirms response shape and mmHg for this account only; it does not establish complete historical coverage or physical-device behavior.
- The observed account's `BPUnit=mmHg` is supported. Other pressure units are rejected until their Personal API representation is verified and explicitly implemented.
- No database schema change is required. v1.3 remains on release hold; automated tests and staging checks do not imply user acceptance.
