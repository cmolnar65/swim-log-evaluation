# v1.3 step 04 — private measurement storage

Schema version advances from 1.2 to 1.3; plugin version remains 1.3-dev. This is an additive dbDelta migration: existing table definitions and rows are not rewritten. New installs and existing installations use Database::install_schema; activation/admin upgrade updates the version only when required tables, new columns and new unique keys are verified. Failed partial creation is retriable. dbDelta DDL is not transactionally rolled back; do not claim atomic schema installation.

## Tables

| Table suffix | Purpose | Identity/index boundary |
| --- | --- | --- |
| health_reports | One current provider/category/day report snapshot, including provider summaries and window/context | Unique user_id + identity_hash; day and source/day indexes |
| health_measurements | One observation group: sample, hourly summary, sleep summary or calculated result | Unique user_id + identity_hash; day and source/time indexes |
| health_report_members | Associate one observation with overlapping reports without copying it | Unique user_id + report_id + measurement_id |

All tables are under the site's wpdb prefix and swimlog_ namespace. No posts, public post types, shortcodes, REST routes, admin screens or public queries are registered for these records. This step provides schema only; validated owner-scoped persistence is step 05, import step 06, calendar access/display steps 07–08.

Custom tables are private by application access boundaries, not database encryption. Existing WordPress database operators/backups can access them. Do not expose generic health-table reads through existing workout APIs.

## Structured content and provenance

summary_json, context_json, values_json and provenance_json are versioned application JSON objects stored as longtext for supported WordPress/MySQL/MariaDB portability. Later service code must validate shape/size/category/role/unit, encode with wp_json_encode and bind all values. These columns are not raw arbitrary Garmin payload archives.

values_json groups related values atomically, each with explicit value/unit and original normalized precision. Blood pressure uses one observation with systolic and diastolic in mmHg, optional pulse as a separate named field, never two independently matched rows. Composition fields from the same measurement share one observation; unknown-unit fields cannot be silently converted or presented as known measurements. BP storage capacity does not imply Garmin Personal API BP support.

Preserve provider, external ID when verified, source measurement context/device when actually supplied, normalization version, timestamp precision and relevant validity/conflict flags in provenance. Never store credentials in these records. identity_hash/content_hash are 64-character SHA-256 hex digests; later persistence must validate canonicalization and separate source identity from mutable content. Hashes are deduplication tools, not anonymization.

The database unique indexes establish concurrency boundaries; identity generation, correction rules, same-owner membership validation and safe writes belong to step 05. No foreign keys are introduced, matching the existing project architecture. Do not assume indexes enforce cross-table ownership or valid JSON. The service must verify both associated rows belong to the same authorized owner before membership insertion, and perform grouped writes transactionally. Non-owner admin access must follow an explicit health-access policy in later calendar work; existing public-results permissions are insufficient.

## Time and calendar fields

- health_reports.provider_date is the provider report's supplied calendar date. summary_json distinguishes provider average/min/latest/sleep/seven-day roles; context_json retains report/sleep window boundaries and original local/GMT strings.
- observed_at_utc is a nullable fixed-format ISO-8601 UTC string (YYYY-MM-DDTHH:MM:SS[.fraction]Z), up to microsecond precision, not a server-local datetime. varchar(32) preserves fractional observation timestamps without requiring fractional SQL datetime support. Later validation canonicalizes the fraction for identity comparisons and rejects unsupported precision rather than truncating it.
- source_local_time preserves the corresponding local timestamp without inventing an offset. source_offset_seconds is nullable and only populated when verified for that instant. Retain unknown/ambiguous source details in provenance, never by guessing UTC.
- calendar_date is nullable. date_basis records provider_calendar, source_local, site_timezone or unresolved under a later allowlist. Do not create a fake day for an unresolved sample.
- For Garmin SpO2 reports, provider_date controls indicator placement as specified in v1.3-spo2-policy.md; sample ownership/report membership rules remain separate.
- For Garmin weight/composition, use verified calendarDate; otherwise a verified local date; only fall back from a verified UTC instant through the swimmer/calendar timezone under explicit site_timezone attribution. Preserve original source evidence. Missing time remains missing.
- created_at_utc, updated_at_utc and fetched_at_utc are ingestion/audit UTC timestamps at second precision; they are not the measurement time or a claimed Garmin modification timestamp.
- A report's identity is owner/provider/category/provider day; changing window boundaries refreshes its current snapshot. Observation fingerprints must not include containing report IDs/dates, so overlap does not duplicate samples.
- No existing workout/calendar date interpretation is changed by installing these tables.

## Migration validation

tests/health-schema-integration.php runs against an isolated synthetic plugin-table prefix in disposable WordPress/MariaDB. It tests fresh installation; a legacy-only 1.2 table set; injected CREATE failure without version advance; retry; legacy table-definition and sentinel-row preservation; grouped BP and source timestamp/offset roundtrip; report/measurement/membership unique keys; separate-owner identities; unresolved nullable dates; repeated installation preserving measurements/reports/membership; detection and repair of missing column/index. It restores the original prefix/version/current user and removes only isolated synthetic tables.

The legacy schema structure is unchanged by this patch. The test creates the same legacy definitions via the unchanged install statements, then removes only the new tables to simulate pre-upgrade storage. It does not claim to replay every historical release installation.

No health readings are imported or displayed in this phase. The remaining runtime warning in the historical calendar fixture remains a separate documented follow-up.
