# v1.3 running and walking: step 1 activity model

Defined 2026-10-29. This is the implementation contract, not enabled import support. Scope is recorded running/walking logs and GPS maps. Swimming remains the sole coaching/evaluation focus. Cycling is deferred until real test files are available.

## Activity identity and environment

Retain existing workout_type values pool and open_water unchanged. Add running and walking as the proposed normalized types in later implementation. Do not create separate sport types based on indoor/outdoor or infer sport from speed, GPS presence, filename or a nearby workout. Existing records must not be reclassified.

A separate activity_environment value has three states: indoor, outdoor, unknown. Unknown means the source has not explicitly established environment; absent GPS does not prove indoor, and available GPS alone does not establish a subtype. Decode source sport/subsport using the official FIT profile and verify Garmin discovery identifiers before enabling them. A generic session with a verified sport can remain running/walking with unknown environment. Unsupported sports and ambiguous multisession/multisport inputs require explicit rejection/review rather than import as swimming.

Cycling must not be accepted by parsers, discovery, scheduled jobs or historical jobs in this phase. Future cycling can use the same general summary/route model, after a separate implementation and real-file validation.

## Proposed normalized record

| Data | Contract / storage direction |
| --- | --- |
| Owner | Existing user_id; all related records belong to the same owner |
| Sport | Existing workouts.workout_type, using running or walking |
| Environment | Separate nullable activity_environment; application representation unknown when absent |
| Start/end | Recorded timestamps through existing time normalization; preserve available source timezone/offset evidence; do not invent an offset from the server default |
| Distance | Recorded total_distance_m in meters and original distance/unit where established; missing stays null, explicit zero stays zero |
| Duration | elapsed_time_ms and moving_time_ms only when independently recorded/semantically verified; timer duration must not be relabeled moving time |
| Device | Existing manufacturer/model when available |
| Heart rate | Recorded average/max may be logged without effort, zone, medical or coaching interpretation |
| Cadence | Preserve only with verified sport-specific units; never reuse swimming cadence semantics without verification |
| Laps/splits | Existing laps with recorded distance/timing and null swimming stroke fields |
| GPS | Existing trackpoints with recorded times, valid coordinates and available altitude/distance; preserve gaps and source ordering |
| Import identity | Existing provider/activity ID, file hash and preserved source association under the existing owner import lock |
| Notes | Existing private notes |
| Swim-only fields | Pool length/course, primary stroke, SWOLF and swim-equivalent steps remain null; no swim lengths/performance evidence generated |

No running pace coaching, race prediction, personal bests, training load, readiness or structured prescriptions are added. Recorded distance/duration summaries are sufficient for initial logging. There is no manual run/walk editor, GPX/TCX expansion or non-swim planning scope authorized by this contract.

## Persistence and migration decision

Existing workout_type is varchar(20), so running/walking do not themselves require a type-column migration. Existing workout, lap, trackpoint and import structures should be reused, subject to step 3 auditing their constraints and semantics.

The current workouts table has no durable environment field. The proposed change for step 3 is a nullable activity_environment varchar column, preserving all old rows as unknown rather than attempting backfill inference. Its actual addition must increment the then-current database schema version and include an idempotent, in-place, data-preserving migration and regression tests. Do not repurpose pool fields, notes, manual structured documents or unrelated metadata to avoid a justified schema change.

Step 1 changes documentation only. Runtime version remains 1.3-dev and current database schema remains 1.3; no migration is implemented or version number reserved/incremented here.

## Import validity and duplicate policy

Require a verified supported sport, owner and usable start time. A legitimate indoor activity may have no GPS or distance. Do not impose open-water distance or saved-location requirements on running/walking. Validate numeric values and chronology; distinguish missing from zero. File/source corruption remains a failure, not an empty successful activity.

Retain owner-scoped provider ID and file hash duplicate safeguards. Summary-based probable matching must also require the same normalized sport; never merge a run, walk or swim across types. Environment disagreements cannot silently overwrite established source evidence. When the same activity arrives through upload, manual Garmin import, automatic sync or historical backfill, preserve source associations, existing retry behavior and explicit review for uncertainty.

A changed Garmin source or conflicting time/distance/type is not automatically a correction. Preserve recorded history and use existing review rules. Missing optional GPS must not erase a previously preserved route.

## GPS and privacy

Reuse the existing open-water map appearance/component, with sport-neutral route data. Display routes only when there are sufficient valid recorded points; otherwise display the summary and a clear no-route state. A single point does not establish a route. Do not interpolate across missing/invalid segments or imply straight connecting lines are measured travel.

Runs/walks do not require a saved swimming location, create a swimming location from a street address, or inherit the open-water proximity/review gate.

Owner authorization applies to summaries, laps, source downloads and GPS endpoints. Existing public swimming/OWS opt-ins do not authorize publication of new land activities or their routes. Initial land-activity visibility is private to the owner; audit existing public shortcodes/REST routes for default-inclusive queries before enabling import. Preserve existing authorized swimming behavior.

## Calendar and swimming isolation

Use clear Run/Walk labels and distinguishable accessible indicators, supporting mobile. Recorded activities remain ahead of measurements, using existing overflow and expanded-day behavior. Swim-only weekly totals, dashboard volume, SWOLF, bests, evaluations and plans must explicitly exclude running/walking; do not rely on every non-open_water row being a pool swim.

The current calendar serializer maps non-open_water records to pool, and several workout methods accept only pool/open_water filters. These are explicit downstream changes for steps 6–7. New record types must not be enabled before those paths and swim-only callers are made safe.

## Steps 2–5 implementation checkpoint

FIT parser 0.3 recognizes sport 1 running and 11 walking, with conservative allowed subsports verified against Garmin's official fit-python-sdk profile.py (profile 21.218). Treadmill/indoor running/indoor walking establish indoor; street/trail/track establish outdoor; generic/casual/speed walking remain unknown. Multiple sessions and cycling remain rejected. Session field 59 and lap field 52 are recorded moving time; field 8 is timer time and is not relabeled. Missing numeric sentinels stay unavailable. Cadence and altitude presentation are deferred rather than assigning unsupported semantics/storage.

Database schema 1.4 adds nullable workouts.activity_environment through the existing dbDelta install/upgrade process. Schema completeness verifies the column, failed upgrades do not advance the version, and legacy rows remain null. Release/runtime remains 1.3-dev. The test ZIP wrapper schema audit is updated accordingly.

Owner-scoped provider/hash duplicates reuse the existing import lock and source associations. Same-sport nearby summary matches require explicit review, never an automatic summary merge. Running/walking never enter pool match queries, evaluations or equivalent-swim-step generation; rebuild and reviewed attachment retain that rule. Existing recorded structure remains authoritative on attachment.

Manual Garmin discovery, scheduled opt-in selections and historical jobs support exact returned typeKey values running/walking, alongside existing swim categories. Subtype aliases are not guessed or included automatically; actual Garmin subtype-key coverage still needs live fixtures/verification. FIT sport is independently decoded. The production gate remains closed until steps 6–7: the internal swimlog_land_activity_imports_enabled filter defaults false and is opened only in disposable integration tests. There is no end-user setting to bypass this staging boundary. Existing swim sync preferences are unchanged, and optional land sync choices default empty. This is implementation groundwork, not a claim that live land imports are enabled or device acceptance is complete.

Private owner-only run/walk details show recorded summary/laps and reuse the open-water SVG route renderer. Missing/invalid points, sequence gaps, reversed timestamps and gaps over five minutes split land routes; no external tile requests transmit coordinates. Indoor/no-GPS records retain summaries. Coaching, derived split analytics, post creation and swim conversion are absent from this detail view.

Committed fixtures are generated synthetic FIT/HTTP responses. Real outdoor run/walk and indoor files remain required for final device acceptance; none have been supplied or committed. Cycling, calendar/list integration and full swimming/public isolation audit remain subsequent work. No release/main/tag/SVN action is authorized.
