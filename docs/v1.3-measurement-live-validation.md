# v1.3 live measurement validation follow-up

On 2026-10-29 the test-site owner reported October 22 weight present in Garmin Connect but excluded by import, plus SpO2 storage validation failures. Only redacted field types, counts, validation codes and table engines were provided; no credentials or raw personal health payload is committed.

## SpO2 numeric precision

The pure adapter allowed positive finite provider doubles with more than nine fractional places, while persistence requires canonical decimals with at most nine fractional places. This reproducibly rejected the entire report with swimlog_health_value. The Garmin adapter now formats floats deterministically to nine fractional decimal places (trailing zeros removed), for SpO2 summaries, weight and BMI. Provider summaries remain provider summaries; this does not calculate new averages. Existing accepted values retain the same canonical stored identity. The storage validator remains strict.

The synthetic HTTP integration now includes repeating/long fractional averages, including duplicate reimport. A pure regression verifies canonical precision and repeatability on the full PHP matrix. Safe storage/validation codes are included in failure messages and import result metadata; SQL, payloads and credentials are not exposed. No schema or version change is required.

## Weight timestamp contract mismatch — compatibility repair

The live response reports integer date and timestampGMT; the official DateWeightDTO inspected again still specifies string date-times for both. The first diagnostic established integer types but not units. A subsequent owner-authorized timestamp-only diagnostic confirmed Unix milliseconds in timestampGMT for the requested date. The personal timestamp value is not copied into repository records or fixtures.

The adapter now supports integer Unix milliseconds specifically for weight/BMI timestampGMT, alongside existing documented date-time strings. It uses integer division/remainder, preserves millisecond precision, emits canonical UTC, and retains provider calendarDate for calendar attribution. Numeric epochs inconsistent with the requested local date (beyond adjacent UTC dates), negative/out-of-range integers, fractional floats and numeric strings are rejected. Generic GMT/SpO2 timestamp handling is unchanged.

When an identical timestamp/value fingerprint already exists, missing optional local-time metadata retains the previously verified stored local time, preserving duplicate detection across response encodings. A supplied different local time remains subject to the existing correction checks.

The separate numeric date field has not established local-wall-clock semantics; it remains excluded rather than assigned a guessed timezone. This optional excluded-field count does not block weight/BMI import. No migration or version increment is required.

Pure regressions use synthetic historical and UTC-boundary timestamps. The actual WordPress integration replays synthetic entries first in documented string format, then integer milliseconds and verifies both weight and BMI skip duplicates.

All three health tables were reported InnoDB. That rules out the engine guard for this diagnostic; it does not prove every database operation succeeds.

Live reimport and calendar acceptance remain pending. v1.3 is unreleased and on release hold.
