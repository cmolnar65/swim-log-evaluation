# v1.3 step 06 — manual Garmin measurement import

The existing Garmin page now offers an owner-only Private measurements form with category selection, inclusive start/end dates and explicit import results. This does not enable scheduled health sync or calendar display. Public APIs, source privacy and existing swimming imports are unchanged. Schema remains 1.3; runtime version remains 1.3-dev.

## Supported and deliberately excluded data

| Category | Imported | Excluded pending verification |
| --- | --- | --- |
| Weight | Each documented kilogram entry with provider calendarDate and a verified timestampGMT | Entries without usable identity/time or mismatched requested day |
| Body composition | BMI in kg/m2 | Body fat/water entry units, muscle/bone mass units, rating fields; no invented conversions |
| SpO2 | Provider average, minimum, latest, sleep/next-sleep and seven-day summary roles, with supplied verified GMT/local window fields | Individual and hourly rows whose descriptor/timestamp contract is unverified |
| Blood pressure | None | No documented Personal API endpoint established |

BMI support is explicitly labeled BMI only. This phase does not claim complete body-composition or raw SpO2 support. The imported provider average is not recomputed from raw/hourly rows. Missing or invalid summary numbers never become zero. A valid summary can be imported while unknown samples/fields are counted as excluded.

The weight all-entries endpoint is requested separately per calendar day, inclusive date/date, and shared between selected weight/BMI adapters within the submission. No contextual adjacent-weight or range-average fields are imported. Provider calendarDate controls placement; timestampGMT is parsed as the documented GMT field, accepting explicit valid offsets or an offset-free GMT string. Local date strings remain local evidence without inferred offsets. Full calendar retrieval/display is steps 07–08.

## Bounds and retries

- At least one of weight/body_composition/spo2 is required; no more than seven inclusive valid dates, ending no later than site today.
- Requests use fixed documented routes and the existing per-user encrypted key/bearer exchange. A request-only token cache avoids repeat token exchange within one submission. No browser credentials are displayed.
- Each measurement GET allows eight seconds, no redirects, and at most 1 MiB of JSON. The existing token exchange retains its 15-second bound.
- A submission stops starting new work after 20 seconds, so it may finish the current bounded request afterward. Remaining category/day rows are Not attempted, not successful. The same range can be retried safely; imported duplicates skip. This is a work-start budget rather than a hard wall-clock guarantee under infrastructure failures.
- HTTP 429 stops further work, accepts a bounded Retry-After waiting period and stores a per-owner cooldown. Retrying during cooldown makes no measurement request. There is no blocking sleep or automatic hammering of failed endpoints.
- Invalid JSON, wrong container shape, oversized/empty HTTP bodies, auth/network/server errors and mismatched provider dates are explicit failures. Valid empty array/object data is No data; supported-structure responses containing only excluded values are No supported values.
- Completed category/day bundles commit independently. A failed bundle rolls back through step 05; earlier completed bundles remain. Failed/empty responses never delete previously imported readings or reports.
- No undocumented endpoint, raw payload, credentials or private extracted content is logged.

## Results and interaction

Results distinguish reading counts (added/updated/skipped), provider report counts (added/updated/skipped), excluded fields/rows, and failed requests/bundles. SpO2 summary import can add a report while adding zero individual readings. No-data, unsupported-only, failed and unattempted outcomes remain distinct. Retry waits are shown explicitly.

The new form has a dedicated nonce and current-owner capability check. No user ID is accepted from the form. Invalid categories, nested malformed fields, future/impossible/reversed/overlong ranges are rejected before transport. No new REST write route is added.

## Validation

GarminMeasurementImportTest covers date bounds, UTC/offset handling, kg/BMI normalization, summary/sample separation and missing/invalid fields across PHP 7.4–8.5. The staged WordPress integration intercepts HTTP with synthetic responses and tests actual persistence/reimport, shared weight requests, timeout/auth/invalid/oversized responses, no-data preservation, owner denial, cooldown and actual form submission/nonce rejection. It does not call Garmin or establish live account coverage. All synthetic user data is removed.

No live credential/payload verification has been performed; importing from a real account is an explicit later user acceptance check. The adapter fails or excludes unsupported fields instead of guessing. No distribution ZIP or release action is performed.
