# Historical Garmin import contract — v1.3 extension, step 1

Status: design contract only, 2026-10-29. No historical-job UI, worker, endpoint or schema is enabled by this step. Runtime remains 1.3-dev; schema remains 1.3. Main/public release remains accepted v1.2. Release hold continues until separately authorized.

## User flow and scope

The current owner selects an inclusive date range and explicit categories on the Garmin page, then starts a private historical import job. Example: 2018-01-01 through 2018-12-31 scans every date in 2018 for the selected supported data. A year must work without a single long-running HTTP request or silently stopping at 100 activities. Existing manual and recent scheduled imports remain available and independent; a backfill never enables recurring measurement synchronization.

| Selection | Import behavior |
| --- | --- |
| Pool swimming | Existing recorded pool-swim FIT pipeline, with existing matching/review rules |
| Open-water swimming | Existing recorded open-water pipeline; require existing verified location matching or explicit location review |
| Weight | All verified individual kg readings, including multiple readings per day |
| Body composition | BMI only until other entry units are verified |
| SpO2 | Verified Garmin provider summaries with existing reporting-window/sleep/baseline distinctions |
| Other activities, blood pressure, uncertain composition fields, raw/hourly SpO2 | Outside enabled transport scope; no inferred values or guessed endpoints |

Activities may include actual recorded FIT evidence only; no planned Workout export may be treated as a completed Activity. Backfill must not change plans, prescriptions, existing recorded swims or PB evidence to force a match.

## Dates and discovery

- Accept strict real YYYY-MM-DD calendar dates, start <= end <= today's site-calendar date, and at least one supported category. Reject malformed/nested/unknown input. Both boundaries are inclusive. A valid full year, including leap years, is required. Do not impose the current manual 7/30-day UI limits on the overall job.
- Job dates/categories are immutable after creation. Changing selection creates a new job. Dates select discovery requests; retain existing Garmin provider/local date and UTC evidence for storage/calendar placement. Never replace source dates with server timezone conversions.
- No undocumented earliest date or unlimited Garmin retention is promised. Larger user ranges must be traversed in bounded windows; any future maximum overall range must be explicit and must permit a full year. No silent truncation.
- Activities: page through each bounded date window using Garmin start/limit controls. Advance by raw provider results, before swim filtering. A page containing only other activity types is not exhaustion. Dedupe repeated source IDs across pages/windows and detect stalled/repeating pagination. A full page is not proof of completion; continue to confirmed exhaustion.
- Check source activity dates against selected inclusive boundaries using documented source-date semantics. Missing/ambiguous dates and malformed pages produce unresolved discovery outcomes, never guessed inclusion or a false clean completion. Pagination boundary/order semantics need verification in step 2.
- Measurements: visit every requested date/category even when local data already exists; existing records do not establish that every source reading has been imported. Reuse verified adapters; weight/BMI share responses where safe.
- Record successful empty dates distinctly from denied, unavailable, malformed, oversized or transport-failed responses. If the API cannot establish historical availability, disclose that limitation rather than claim the user had no measurements.
- A scan establishes what Garmin returned during that execution, not a permanent snapshot or proof that all historical records ever recorded remain accessible.

## Duplicate, correction and retry decisions

| Existing/source state | Required outcome |
| --- | --- |
| Successfully imported same owner/Garmin activity ID with valid associated workout | Already present; no second workout or FIT download solely to reimport |
| Existing activity ID whose import failed or association/workout is incomplete | Examine actual status/integrity and use a safe retry/repair path; ID existence alone is insufficient |
| Activity already pending match/location review | Keep one pending item and link to existing review; do not create another or silently mark imported |
| Byte-identical existing FIT for same owner | Reuse existing safe association rules after checking import status; no duplicate workout |
| Possible semantic match with different FIT bytes or ambiguous identity | Existing conservative matching/review; no automatic deletion, merge or overwrite |
| Exact measurement fingerprint repeated in stream, window, manual, scheduled or historical import | Skip duplicate persisted observation; calendar displays once |
| Same value at different timestamps | Retain distinct readings |
| Changed same-time observation without verified stable identity | Preserve/flag ambiguity under existing policy; do not guess a correction |
| Identifiable newer provider report or verified stable-ID correction | Existing validated update/CAS rules; no additional calendar entry |
| Missing source item, empty date or failed request | Preserve existing records; absence never authorizes deletion |

Pending, failed and successfully imported are separate statuses. Failed items must remain retryable; retries must not reimport completed units unnecessarily. Summary refreshes remain permitted because this is required for accurate provider reports. Previously imported activity content is not automatically rebuilt or refreshed in this scope.

Concurrency with manual, regular sync and overlapping backfills must be safe at the persistence boundary, not merely through a job lock. Recheck identity/status when committing. Activity duplicate concurrency guarantees must be inspected and strengthened/tested if necessary before bulk execution is enabled.

## Ownership and controls

- Current-owner authentication/capability and action-specific nonce protect creation, status, review links and controls. Never trust a posted owner ID. Administrator/manage-all capability does not independently grant access to another swimmer's health jobs/data.
- Worker resolves immutable owner from trusted persisted job configuration, rechecks relevant permissions, opt-in/job state and configured key, and restores any temporary WordPress user context in finally. New backfill authorization must not weaken existing API/storage/calendar boundaries.
- Permission loss, missing/revoked credentials or authorization failure blocks work with an actionable status. Do not discard job history/cursor as though scanning completed. Resumption rechecks authorization.
- One unfinished historical job per owner, including paused or blocked jobs; overlapping requests direct the owner to resume or cancel that job. Later re-runs of completed/cancelled ranges remain duplicate-safe.
- Start/Resume schedule bounded work. Pause stops new work at the next safe boundary and preserves the cursor. Cancel is terminal for that job and stops future work without undoing imports. An already-started operation may finish; state/generation checks prevent stale workers restarting paused/cancelled work.
- Retry Failed retries unresolved failures while retaining successful progress. It does not create duplicates or automatically approve review items. Cancelled jobs require a new job to scan again.
- Survive tab closure, logout, process termination and WordPress restarts. Cron depends on site traffic, with visible missing-task/blocked status; do not promise exact completion time.
- Use bounded batches, owner/job locks, checkpointed pagination/work queues, response limits, rate-limit waits and bounded automatic retries. Exhausted failures remain visible for explicit retry. No tight polling or repeated calls during a known cooldown.
- Persist configuration, cursors, normalized counts, safe errors and necessary private review/retry references only. Credentials/raw health payloads must not enter job logs, public REST, packages or Git. Sensitive job metadata is owner-scoped and not exposed through existing portability/public routes.

## Progress and completion

Job lifecycle: queued, running, waiting (rate limit/backoff), paused, blocked (authorization/configuration), completed, completed_with_errors, cancelled. Review counts are outcomes independent of lifecycle; a cleanly scanned job can finish with clearly visible pending review.

Progress must distinguish activity discovery windows/pages, discovered/imported activity items, and measurement date/category units. Do not invent an activity total or percentage before discovery establishes it. Counts from retries must reflect logical work items, not add the same success repeatedly; network attempt counts, if shown, are separate.

Show imported, already present/duplicate, updated provider reports, needs review, successful empty, excluded unsupported data, failed/unresolved and remaining work. Separate activity, report and individual-reading counts rather than combining unlike units. Review links must preserve owner authorization.

Completed requires all windows/pages exhausted, every selected date/category attempted successfully and every discovered supported activity resolved to imported/already-present/review. No failed/stalled/unattempted discovery or import work can be hidden as success. Completed_with_errors means reachable work has finished but unresolved discovery/import failures or retry exhaustion remain; an incomplete scan must be explicit. Disclose review/exclusion counts even when no errors remain. A blocked, paused or cancelled job is never labelled complete. Retain a safe final summary and retry information.

## Acceptance and implementation gates

1. Synthetic full 2018 traversal, leap-year and inclusive first/last-day cases.
2. More than 100 activities, mixed/non-swim pages, repeated pages/IDs, boundary dates, and discovery failure without false completion.
3. Imported vs failed vs incomplete vs pending activity records; exact FIT and ambiguous matches; open-water location review; concurrent sources.
4. Multiple/day measurements, duplicate overlaps, report corrections, same-instant conflicts, source-day/UTC boundaries and DST without invented averages.
5. Timeout/restart/resume, rate-limit waiting, partial failure and Retry Failed; accurate counts after repeats.
6. Pause/cancel during HTTP, settings/permissions/key changes and stale-worker protection.
7. Owner/nonce/job-reference isolation, no public exposure, mobile controls and accessible status/review navigation.
8. Full PHP 7.4 and 8.0–8.5 checks; strict actual production staging Plugin Check with diagnostics inspected; existing swimming/calendar regressions.

Live-account history and endpoint limits remain verification limits, not automatic acceptance claims. Synthetic tests must not require real credentials or confidential PDFs. A new schema version is allowed only if later job storage actually requires a schema change; that decision includes an additive, idempotent, in-place migration with preservation/regression tests.
